## 1. 先把领域从零讲清楚

这一节不带任何滤镜，就是最朴素的概念。你不需要会写代码，只需要愿意接受几个比喻。

### 1.1 什么是 DSH（DeepSeek Harness）

DSH 是一个**本地的 AI 智能体（agent）服务**。

「智能体」在这个语境下 = 一个 AI，它不只是跟你聊天，还**会动手干活**：改文件、跑命令行、查资料，一步步完成一个任务。DeepSeek Harness（简称 DSH）就是干这个的东西，它跑在你自己的电脑上，默认在 `http://127.0.0.1:3080`。

可以把它理解成：**一个住在你电脑里的、会做事的 AI「工人」**。

### 1.2 它是「服务」，不是一个应用

关键认知：DSH 不止是一个你能双击打开的软件，它更像一台**服务器**。它对外提供两样东西：

- **一个 RPC 网关**（`POST /api/<endpoint>`）：你叫它干活、问它状态，走这里。请求体是一个「信封」——`{type:"client-request", rpcId, method, payload:{args}}`：方法名（`session/list`、`session/prompt`…）、参数、以及一个用于对账的 `rpcId`。
- **一条多路复用的事件套接字**（`/api/remote.mux`，一条 WebSocket）：它干活的过程——用了哪个工具、改了哪些文件、说了什么——以一条条带序号（seq）的「事件帧」持续推给你。同一条 WebSocket 上跑着若干条**逻辑流**：全局 `$events` 流（审批、提问、会话级信号）、按会话的 `session/control`（历史与状态投影）、`workspace/follow`、`session/follow` 等。

这两样合起来，就是 DSH 和「外面的人」交流的全部方式。

### 1.3 什么是「协议」——你和 DSH 说话的方式

DSH 说一种**约定的“语言”**，官方把它定义得很清楚（官方 README 原文就叫它 "wire contract"，协议契约）。这语言一共四种消息：

| 消息 | 谁发起 | 走哪 | 干什么 |
|---|---|---|---|
| `ClientRequest` | 客户端 → 服务端 | `POST /api/<endpoint>` 信封 | 你叫它干活（带 `rpcId`） |
| `ServerResponse` | 服务端 → 客户端 | 那个 POST 的响应体 | 告诉你结果（`result.ok` / 失败错误） |
| `ServerRequest` | 服务端 → 客户端 | `$events` 流里的 waterfall 帧 | 它反过来**问你**（如 `approval/request`：「要不要允许这个操作？」） |
| `ClientResponse` | 客户端 → 服务端 | `POST /api/$events/result` | 你回答它的问题（带上 `clientId` + `eventId` + 结论） |

**两条铁律**：

1. 每次回应都**原样带回请求方的 `rpcId`**，绝不自己造一个新的——这是对账的依据。
2. 回答 waterfall 问题时，必须带上**事件流 ready 帧里下发的 `clientId`**——这是「认领」：证明你就是被问的那条连接。带错了，网关会直接拒绝（`invalid Remote event result`）。

> 一句话：**协议就是「双方都认的那套约定」**。谁按这套约定来，谁就能跟 DSH 顺畅交流，不管你是浏览器、命令行，还是别的什么。

### 1.4 什么是「桥接」——为什么是「第二个客户端」

DSH 自带一个**网页界面（Web GUI）**。那个网页，本质上就是 DSH 的**第一个客户端**——它用上面那套协议跟 DSH 说话，把聊天框、工具调用、事件流画出来给你看。

**这就是整个项目的核心洞察**：

> 网页能做的所有事，靠的只是「那套协议」。既然协议是公开约定的，那我**也能**用同一套协议做一个客户端——**不必是网页，可以是 VS Code 侧边栏**。

于是这个项目「链接」了 DSH 和 VS Code，但它**没有重写 DSH**，也没有**另起一个 DSH**。它只是**多了一个看懂 DSH 协议、并把内容用 VS Code 的方式呈现出来的“客户端”**。

这就叫**桥（bridge）**：一脚踩在 DSH 的协议这一端，一脚踩在 VS Code 这一端，中间只传话，不改 DSH 本体。

### 1.5 什么是「插件框架」——官方 UI 是怎么长出来的

DSH 的官方网页界面，不是一张死页面。它是一个**运行时（runtime）+ 一堆插件**组成的框架：

- **runtime**：管加载、管连接、管把消息路由给谁。
- **插件集**：会话列表、聊天框、工具栏、设置页……这些 `client-ui-*` 都是独立插件，只属于官方的 runtime。

官方 UI 每次「换了个样子」，本质上是**插件集更新了**（插件整体升级换代）。

我们连官方插件管理的能力也直接复用：设置页的「插件」标签就是调官方 `pluginManager/*` 这组 RPC——检索、安装、启停、卸载、版本豁免，全是官方接口，我们没有自己发明一套。

这就是 §3.3 的关键铺垫：**UI 是容易变的，协议是稳定的。**

## 2. 这个项目的定位

### 2.1 一句话定位

> **它是 DSH 的一个「好客户端」——只做协议对岸的翻译，不碰 DSH 的本体。**

它把 DSH 的**真实能力**（会话、模型、工具、审批、提问）用 VS Code 的方式重新呈现，同时**保留** DSH 最珍贵的东西：**一份历史、一套契约、官方本体一行都不改**。

### 2.2 三条边界（不做什么，以及为什么）

| 不做 | 为什么 |
|---|---|
| **不重写 DSH** | 官方本体是「字节级一致」的（npm 发布原版）。它多稳，你就多稳；它升级，你不用跟着大改。 |
| **不复制/模仿官方 UI 框架** | 模仿框架＝替官方再维护一遍插件系统，既不讨好官方，也累死自己。 |
| **不另起第二个 DSH** | 两个 DSH 共用一份历史日志，会互相写坏（这是真实踩过的坑：`corrupt session log: seq gap`）。扩展只复用正在运行的 harness；确实没有时才自启一个**从属实例**，并保证 VS Code 退出时把它确定性关掉；手动启动的 harness 永远不碰。 |

守住这三条，才谈得上「纯桥接」。

## 3. 四个关键设计

这四块，就是这套设计最硬核、也最难被别人复制的部分。**它们共同证明：这不是一个「把网页塞进侧边栏」的取巧实现，而是一个真正的协议级客户端。**

### 3.1 拼图一：HarnessClient —— 不到 300 行

`src/harness/client.ts` 是整套桥接里最核心的一个文件，**不到 300 行**。它是官方浏览器端「client-runtime」的一个**最小 Node 移植**：

- 实现的是**和浏览器完全相同的协议**（typert 信封、`rpcId` 对账、waterfall 应答）；
- **不 import 任何 DSH 内部包**；
- 只要 Node ≥ 18（`fetch` 是全局的）就能跑；事件套接字用 `ws`（VS Code 的宿主 Node 对新协议的 WebSocket 支持才够稳）。

行数少不是偷懒，而是**它足够薄**。官方把「协议的所有不变量」封装在客户端基类里，我们这不到 300 行就是在 Node 里把这套协议重新最小实现了一遍：历史分页（`session/page`，按 `throughSeq` 翻页）、按会话**投影**（模型选择、权限、用量、待办……随历史尾页和实时增量一起推送的「当前状态快照」）、以及一个**三态探活**（正常 / 未授权 / 不可达——把「API 拒绝访问」和「服务没起来」分开，这个区分决定了自启策略）。

> **价值**：别人写一个「DSH 插件」，要先读懂官方整个插件框架。你写一个「DSH 客户端」，只需要读懂**协议本身**。前者重，后者轻；前者跟着 UI 变，后者跟着契约走。

### 3.2 拼图二：PanelEvent —— 原样转发，不做重新建模

`src/panel/protocol.ts` 里的 `PanelEvent`：

- 它**几乎就是** DSH 推来的原始事件帧 —— 类型、序号、时间、数据原样带过来；
- 面板拿到的是一个**未经二次加工的原始帧**，**渲染层的解释由面板自己完成**；
- **桥接层在中间不做任何「重新建模」**，不把事件改造成另一套自己发明的结构。

> **价值**：桥接层越「透明」，越不容易跟官方语义脱节。官方一个事件是什么意思，我们这里还是什么意思。这叫**无损**——信息在桥这头到那头，一个字节都没被自作主张地改造。

### 3.3 拼图三：消费同一份协议契约 —— 官方 UI 怎么变我都不怕

这是整套设计最值钱的地方。

DSH 官方界面 = **runtime + 插件集**。官方每换一次 UI，本质是**插件集整体换新**。而我们的项目：

> **消费的是协议契约，不是官方 UI。** 只要协议不变，官方 UI 无论怎么改版、插件怎么疯狂升级，我们都**不需要跟着改**。

——因为**协议是官方向客户端承诺的契约**（"wire contract"），它是稳定的；而**UI 只是这份协议的一种消费方式**，它是会变的。

这套立场不是口号，是有实据的：DSH 从 0.1.7-rc.2 到 0.2.0-rc.2 经历了一次**协议大改**（路由体系、事件流多路复用、审批应答通道全换），本扩展的适配被牢牢圈在**客户端与映射层**（`client.ts` / `protocol.ts` / 事件流解析）——面板的渲染语义、编辑器桥、会话管理等上层几乎原样存活。这正是「协议优先」的红利。

（官方 README 也写明：*没有协议版本字段，因为客户端与服务端一起发布——直到出现独立发布的客户端*。本扩展正是那个独立发布的客户端之一。）

### 3.4 拼图四：overlay —— 唯一的「临时侵入」，且被严格隔离

这是四块拼图里**唯一不是纯协议**的一块。

有**一个**能力，DSH 的协议**没有对外开放**：**本地第三方客户端通过进程级浏览器鉴权的通路**。DSH 0.1.7-rc.2 起，`/api` 与事件套接字都要求浏览器登录态（token/cookie）——这是为了防住「随便一个网页就能操作你本机 agent」的正确设计，但顺带也把「第三方独立客户端」这条路堵死了。官方不提供「非浏览器客户端」的凭据通路，我们只能**垫一个临时补丁**把这个检查对本地回环请求放开。

它不是插件，是**对官方进程内部的一次临时侵入（monkey-patch）**。详见下一节——怎么让它「侵入」得可控、可回滚、绝不坏事。

## 4. 唯一的技术取舍：overlay 补丁

它说明 overlay 为什么存在、如何保证安全、以及何时退役。

### 4.1 它是什么，为什么存在

DSH 有一套**运行时补丁机制（overlay）**：在官方进程**加载模块的瞬间、在内存里**替换掉一段代码。当前 overlay 里只有**一个 delta**：

| delta | 作用 | 为什么需要 |
|---|---|---|
| `client-connection / browser-auth bypass` | 对**本地回环**请求跳过浏览器 token 检查 | DSH 0.1.7-rc.2+ 要求浏览器登录态才接受 `/api` 与事件套接字连接；第三方协议客户端（如本扩展）拿不到浏览器凭据。没有这个放开，扩展连接即 401。 |

**这个机制是怎么来的？** 两段真实经历逼出来的：

1. 2026-08 发生过一次真实事故：扩展自拉了一个 DSH（3081 端口），和网页端的 DSH（3080 端口）**共用同一份 `~/.dsh` 历史目录**。两份日志没有跨进程锁，两个进程各自的内存序号交错排写，结果日志被写坏（`corrupt session log: seq gap`）。修复方向就一个字：**不让你抢**——扩展只做「第二个客户端」，绝不做「第二个服务端」（见 §2.2）。
2. 0.1.7-rc.2 的浏览器鉴权上线后，连接全面 401。协议没有存量替代通路，overlay 就是面对这道墙的唯一出路。

### 4.2 为什么它被允许：三条安全护栏

补丁危险，所以给它上了三把锁：

1. **内存篡改，不碰磁盘**：补丁在官方模块**加载进内存的一瞬间**换掉源码，**磁盘上的官方文件全程只读、一行不改**。进程退出，补丁就消失。官方安装树始终是「字节级一致」的 npm 原版。
2. **SHA 校验，不对就整体放弃**：启动时校验官方文件的 SHA256，万一跟 npm 发布版对不上（官方升级了、被别人改过），**整个补丁跳过**，进入降级模式——绝不硬着头皮去 patch 一个不认识的文件。
3. **金丝雀锚点，变了就退**：哪怕 SHA 通过了，patch 前还要确认「官方源码里我认识的那几行还在」。找不到，就记一条 `CANARY-FAIL`，**放弃这次补丁**，正常降级跑。

> 降级后最坏会发生什么：连接被 401 挡在门外，面板显示「API 拒绝访问」，并提示「overlay 补丁与当前 DSH 版本不匹配，请更新扩展」——**看得见、说得清、不静默**。校验失败永远不致命。

### 4.3 它的「退出条件」

这套补丁是**一次性的临时解决方案**，有明确的退役标准：

> **等官方为「独立客户端」提供受支持的鉴权通路（headless token / 服务凭据 / 配置开关），就删掉这个 delta。** 在那之前，它是我们和「完全不改官方」之间唯一的一步妥协；在那之后，overlay 整个被移除，项目真正做到 100% 纯协议、零侵入。

**结论**：项目只在一处动官方——而且那处是被迫的、有护栏的、有退役路线的——**其余全是协议，一分不少。**

## 5. 生命周期与工程机制

协议以外，这个扩展还有几处值得讲的工程机制——它们的共同点是：**尽量让用户「无感」，出错时「说清楚」。**

### 5.1 harness 生命周期：发现 → 复用 → 自启 → 确定性关闭

- **发现**：启动时先探测配置地址（默认 3080）。三态结果——正常 / 未授权 / 不可达——分别走不同策略：正常就复用；未授权会提示「API 拒绝访问」（多半是 overlay 失配，见 §4.2）；不可达才考虑自启。
- **自启**：从全局 npm 安装里解析 `@deepseek-ai/dsh` 的真实入口（绕过 npm 的 `.cmd` shim，避免弹出黑窗口），以**无窗口、分离进程**方式启动，注入 overlay 与 PID 记录。
- **确定性关闭**：自启的实例是**从属（owned）**的——VS Code 退出（窗口关闭 / 重载）时按记录的 PID **确定性停掉**；配套 PID 复用护栏（对命令行里 `--port <port>` 二次核对），绝不误杀别人的进程。手动启动的 harness 永远不在清理范围。
- **孤儿治理**：若上次进程被强杀（deactivate 没跑到），下次启动会认出这个「孤儿」并复用或接管，而不是又拉起第二个。
- **冷启动容忍**：大版本更新后（npm 换掉整棵依赖树），harness 冷启动实测可达 ~45 秒；重启验证路径给了 90 秒启动窗口 + 45 秒验证重试窗口，避免把「还在启动」误判成「挂了」。

### 5.2 更新中心：先预检，再升级，失败能回滚

DSH 更新很频繁，而每一次协议改动都可能让扩展失配。所以「更新 DSH」在这里不是一句话的事：

1. **检查**：启动时查 npm registry，发现新版本弹窗（「暂不更新」记忆到下一个版本）。
2. **接口预检**（升级前）：
   - **通告扫描**：把官方 Release Notes 里当前版本 → 目标版本之间的说明抓下来（GitHub API，失败回退 atom），逐条扫本扩展用到的**接口标识**（33 个：全部 RPC 端点 + 事件流协议名 + 鉴权协议名）。
   - **包内核验**：把目标版本的 tarball 拉下来，**静态**检查这些接口是否真的存在于三个关键官方包里（`dsh-api-remotes` / `dsh-api-gateway` / `dsh-client-connection`）。
   - **三分支**：有风险 → 警告并建议「先更新扩展，等适配」；通过 → 正常弹更新；预检不可用（断网等）→ 照常弹更新，但如实说明「预检未完成」。无论如何都保留逃生通道：*仍要更新（自检失败自动回滚）*。
3. **执行**：停掉从属 harness → `npm install -g` 目标版本（超时保护、输出留日志）。
4. **自检**：重启 harness → 探活 → **验证 RPC 与事件流都通了**才算成功；失败 → 提供「回滚到原版本」按钮（重装旧版 + 重启 + 再验证）。

### 5.3 Windows 沙箱 ACL：一次性把地修平

DSH 的 `workspace-write` 沙箱在 Windows 上靠 ACL 实现：执行前要给工作区目录**写一条低完整性标签 + 授权沙箱账户**（一次 `SetNamedSecurityInfoW`）。写标签需要目录的 `WRITE_OWNER` 权限——而**从旧机器拷来的目录**（owner 是别的账户/SID）恰好没有这个权限，于是沙箱启动直接失败（`SetNamedSecurityInfoW failed (Win32 5)`），表现为「代码执行永远失败」。

扩展的修法：打开/切换工作区时自动尝试 `icacls` 授权（当前用户完全控制，全树继承）；能修就静默修好（顺手消掉「换工作区就失效」的问题）。确实修不了（目录 owner 是系统/别的账户）→ 弹一次警告，提供**管理员一键修复**（UAC 提权跑同一条授权）。

### 5.4 跟随编辑：光标落在真正改动的行上

「agent 改了哪个文件」在协议里有现成事件，但「改了哪一行」没有。跟随编辑用了一个朴素而可靠的办法：

- **记住改动前的内容**：工具调用（直接 `write`/`edit`/`apply_patch`…，以及 PTC 模式下通过 `tool/ptc-dispatch(-start)` 暴露的嵌套写入）一出现，就把目标文件改前文本读进内存。
- **改动后再读一遍**，按行做公共前缀比较，**第一个不同的行号**就是目标。
- 打开文件用**预览标签 + 不抢焦点**（你正在输入时不会被拽走），并把光标定位到那一行。

覆盖范围与边界（shell 里手写的文件追不到）如实写在 README 的「边界」一节——宁可说清楚，不做「看起来全能」的承诺。

## 6. 它在生态里怎么立得住

一套设计好不好，取决于从谁的角度看。从三个角度——官方、用户、架构——看它是怎么立住的。

### 6.1 官方的视角

官方最看重的是：**你尊重我的协议、不改我内部、做得很薄很稳。**

- 一个**不到 300 行的协议客户端 + 自己画的界面**，比一个**模仿插件框架的壳**更让官方喜欢——因为后者是在「重新发明人家的轮子」，前者是在「**真正用人家给的路**」。
- 而且你**给协议提供了一个真实的使用场景**：一个独立发布的第三方客户端，本身就是对官方协议完备性的压力测试——哪块协议缺了东西（比如「非浏览器客户端」的鉴权通路），我们第一个撞上，也第一个反馈。

### 6.2 用户的视角

用户不关心架构形制，他们关心两件事：

- **开箱即用**：装了就能用，不用重输 API key；更新有预检、失败能回滚，心里有底。
- **界面质量**：看起来顺手、干起活来清晰。

我们两者都占了——`dsh-vsc` 是原生 VS Code 面板 + 编辑器右键提问 + 跟随编辑，不是塞一个浏览器 iframe 完事。

### 6.3 架构的视角

真正懂架构的人，看重的是**能不能立得住**这三个词：

1. **接口稳定**：协议契约不动，你我就不慌；协议真动了，适配也有预检和回滚兜底。
2. **关注点隔离**：协议层、渲染层、侵入层（overlay）分得清清楚楚，各管各的，互不污染。
3. **组合优于继承**：不硬造一套「插件框架」去套，而是用「协议总线 + 单元」这样的组合方式，自然生长。

这些**正是插件框架的实质**。我们用**文档 + 边界**证明了同样的实质，而不用真的去造一个框架。

> **结论**：「模仿 UI」和「遵从协议」是两回事。这套设计遵从的是更底层、更本质的那一层。

## 8. 你可能被问到的问题

**Q：你这不是模仿官方插件框架吗？**
A：不是。模仿框架是「重新发明官方那套插件系统」，那既重又容易跟官方脱节。我做的是「**遵从官方的协议契约**」——这比模仿 UI 更本质。有意思的是，官方的插件管理能力我反而直接复用：设置页的插件标签调的就是官方 `pluginManager/*` 接口，一行自造的轮子都没有。

**Q：你说不动官方，那个补丁是什么？**
A：那是唯一动官方的地方，**一个 delta**：DSH 0.1.7-rc.2 起要求浏览器登录态才接受本地 API/事件流连接，第三方客户端拿不到浏览器凭据，补丁对**本地回环**请求放开这个检查。有三层护栏：只在内存里改、SHA 不对就整体放弃、锚点找不到就降级（降级会明确提示，不会静默）。官方文件全程只读。等官方给出正规的非浏览器鉴权通路，这个 delta 立刻删。

**Q：DSH 一升级你会不会坏？**
A：要看升的是哪层。**升级 UI（插件集）→ 跟我无关**，因为我消费的是协议不是 UI。**升级协议（契约）→ 那才是唯一需要适配的信号**——而且扩展内置了「更新中心」：升级前自动做接口预检（扫描官方通告 + 核验新版本包内接口），有风险会先劝你更新扩展；升级后自动重启自检，失败一键回滚。0.1.7 → 0.2.0 的协议大改已经实证过一次：适配只发生在最薄的客户端层。

**Q：为什么不直接把官方网页嵌进侧边栏就行？**
A：做是可以，但那是「壳」，不解决「你选中代码要问 AI」这类 VS Code 原生交互。真正的价值在**原生桥**：编辑器右键提问、跟随编辑定位到改动行、审批/提问卡片、工作区集成——这些只有做一个协议客户端才能拿到。

**Q：那 API key 呢？**
A：不用在插件里配。key 与账号都在 DSH 那边管着，我只是它的一个客户端，**不碰你的 key**。

**Q：为什么不用官方 SDK / 官方客户端库，非要自己复刻协议？**
A：官方没有对外发布「独立客户端 SDK」；浏览器端的 client-runtime 和官方 UI 是同一套发布物、深度耦合。复刻协议（而不是引入官方 UI 代码）恰好是「纯桥接」的立场：只依赖契约，不依赖实现。

### 9.1 术语表

| **typert 网关** | 新版 RPC 入口：`POST /api/<endpoint>`，`{type:"client-request", rpcId, method, payload:{args}}` |
| **客户端 client** | 用协议跟 DSH 说话的一方（网页 / 本扩展 / 命令行） |
| **事件帧 event frame** | DSH 干活过程推给你的一条条带序号的消息 |

| **waterfall** | 服务端反问客户端的流程（审批、提问）；应答经 `POST /api/$events/result`（带 ready 帧 `clientId`） |
| **projections（投影）** | 随历史尾页/实时推送的「当前状态快照」（todos、permissions、模型选择…） |

| **PTC 嵌套调用** | PTC 模式下 `run_code` 内部调用工具，经 `tool/ptc-dispatch` 事件暴露 |
| **overlay** | 运行时内存补丁机制，唯一动官方处；当前只有 1 个 delta（浏览器鉴权 bypass） |
| **接口预检** | 更新前扫描官方通告 + 静态核验新包接口的护栏流程 |
| **原生桥** | 选中代码提问、改动文件跟踪、跟随编辑等 VS Code 原生集成 |
| **pure bridge（纯桥接）** | 只做协议对岸翻译、官方本体一行不改的设计原则 |
